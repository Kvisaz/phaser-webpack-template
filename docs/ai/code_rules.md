Это критически важные правила, следуй им тщательно!

# Как писать код

Стремимся к минимализму, KISS, YAGNI подходам - но не забываем о хорошем раскладывании на  слои абстракции. В проекте  в папке src используются такие слои - от самого общего к самому конкретному 

- /common - самые общие подходы, не зависящие от проекта
- /logic - логика и типы конкретной игры
- /services - сервисы конкретной игры
- /assets - виджеты, игровые элементы, доступ к конкретной графике и звукам
- /scenes - место где все собирается в конкретные экраны

Импорты могут быть только из более общего, более высокого слоя абстракции

Пишем код в расчете на Phaser 3.90 и TypeScript 4.5.5 - это наш стабильный сетап.
Для новых функций, методов и классов обязательны комментарии `/** ... */` на русском языке.
Комментарии `/** ... */` на русском языке обязательны для ключевых моментов кода, отвечающего за сложную верстку нескольких объектов, математические вычисления и сложные логические комбинации.
Старые комментарии не удаляем, если это не было отдельно запрошено.

Phaser уже подключен как статическая библиотека, его не надо импортировать.

Всегда типизируем, максимум позволяем себе Unknown.

Стараемся писать код, разбивая его на отдельные модули, функции, классы. Складываем такие нужные модули в подпапку в папке с основным кодом. Используем индексный файл для реэкспорта.

## Папки и импорт

Термины:
- Слой — уровень абстракции (`common/logic/services/assets/scenes`).
- Фича — законченная область поведения игры.
- `shared` — код внутри слоя, который используется минимум двумя фичами.

Правила импортов:
- Импорты только “вверх по слоям”: из более конкретного в более абстрактный.
- Внутри слоя — из своей фичи или `shared`.
- Межфичевые связи — через фасады (например, центральный сервис) или `shared`.

Пример папок (условный):
```
src/
  common/
  logic/feature-a/
  services/feature-a/
  assets/feature-a/
  scenes/MainScene/
```
Пример импорта: код в `scenes` может импортировать из `assets/services/logic/common`,
а код в `logic` — только из `common`.

Cкладывай типы и интерфейсы всегда отдельно в types.ts, за исключением props - которые должны лежать рядом с компонентом. Под props понимается и любой объект который используется как аргумент для любых функций или инициализаций конструктора класса.

Константы для компонентов и сложных кусков должны лежать в constants.ts
Но для небольших файлов и функций - константы могут лежать сразу рядом, в начале файла.
Если связанных констант больше одной, не пиши их набором `SOME_CONST`. Объединяй в объект `someNameConfig = { ... }`.

##  event bus
- код под src/scenes - IGameEvents из src/events
- код в src/common - каждый модуль имеет свой локальный `events.ts` и связанные с ним локальные типы. Их нельзя экспортировать через `index.ts` и импортировать в другие модули. Если нужен совместимый event API в другом модуле - объяви у него свой локальный интерфейс с теми же event names и payload.
- Для отправки и подписки используем `SceneEvents<...>`. Если объект умеет `destroy`, передавай `autoUnSub`.
- Если модулю нужно запросить данные у другого модуля через events - по умолчанию используем пару событий `requestX` и `responseX`.
- Оба модуля объявляют у себя локальный совместимый интерфейс с одинаковыми event names и payload, без импорта чужого `events.ts`.
- На стороне отправителя сначала подписываемся на `responseX`, потом делаем `emit("requestX", data)`.
- На стороне приемника слушаем `requestX` и в обработчике эмитим `responseX`.
- `requestId` добавляем только если реально возможны несколько одновременных одинаковых запросов с одним и тем же `responseX`.
- Ссылочная типизация вида `SomeType["field"]` запрещена. Объявляй явные `type`/`interface` и используй их. ИСКЛЮЧЕНИЕ - приведение к типу внутри switch case - там можно!

Пример локального `events.ts`:
```typescript
export interface ICardThemeControlsEvents {
  cardThemeFaceChange: { faceAssetName: "chibi" | "classic" };
  cardThemeBackChange: { backAssetKey: string };
}
```

Пример отправки:
```typescript
const events = new SceneEvents<ICardThemeControlsEvents>({scene});
events.emit("cardThemeFaceChange", {faceAssetName: "classic"});
```

Пример подписки в другом модуле без импорта чужого `events.ts`:
```typescript
export interface IGamePlayCardEvents {
  cardThemeFaceChange: { faceAssetName: "chibi" | "classic" };
  cardThemeBackChange: { backAssetKey: string };
}

const events = new SceneEvents<IGamePlayCardEvents>({scene, autoUnSub: this});
events.on("cardThemeBackChange", (data) => {
  this.setBackThemeByKey(data.backAssetKey);
});
```

Пример request/response:
```typescript
export interface ICardInfoRequesterEvents {
  requestCardInfo: { cardId: string };
  responseCardInfo: { cardId: string; title: string; cost: number };
}

const events = new SceneEvents<ICardInfoRequesterEvents>({scene, autoUnSub: this});

events.once("responseCardInfo", (data) => {
  if (!data) {
    return;
  }

  this.showCardInfo(data);
}, 3000);

events.emit("requestCardInfo", { cardId: "card-1" });
```

Пример `index.ts`:
```typescript
// good
export * from "./GamePlayCard";

// bad
export * from "./events";
export * from "./types";
```

## Наследование и ООП
Геттеры и сеттеры по умолчанию запрещены - нужны только такие публичные методы, которые выполняют полезную функцию и инкапсулируют скрытые механизмы.

Публичные методы пишем после конструктора и метода destroy, private - после публичных.

### State/StateConnector
- Общий стейт держим в одном экземпляре `State<T>` (напимер в `src/logic/state`), наружу отдаём через `StateConnector` для изолированных подписок/отписок.
- Подписчики должны быть устойчивы к исключениям: окружение оборачивает вызовы в try/catch и логирует в консоль.
- `await()` у `StateEvent/State` отменяется через `unSubScribeAll` (промис реджектится), учитывайте это в вызывающем коде.
- Не раздувай код опциями — добавляй только то, что реально используется сейчас (KISS).

## KISS — Keep It Simple, Stupid

Делай проще — выбирай самое понятное решение, работающее сейчас.

- Не вводи абстракции и конфигурацию заранее; повторяемость ≥ 3 раз — тогда выносим.
- Маленькие, одноответственные модули/функции/компоненты с явными входами и выходами.
- Предпочитай простые типы и явные интерфейсы вместо избыточной дженерик-магии.
- Явность важнее хитрых трюков: избегай скрытых побочных эффектов и длинных цепочек.
- Если код можно объяснить за 30 секунд — он достаточно простой.

## Аргументы как props объекты

Если функция или конструктор требует больше двух полей - используем как аргумент props - то есть объект с нужными именованными полями.

Это позволяет легко вспоминать их при наборе, а также использовать готовые аргументы.
Для локального интерфейса props используем имя `I[name]Props`. Если props не деструктуризируется сразу, делаем его private в классах.

```typescript
interface IMyFuncProps {
  scene: Phaser.Scene;
  text: string;
  x: number;
  y: number;
}

function MyFunc({ scene, text, y, x }: IMyFuncProps) {
  // используем аргументы
}
```

## Размеры и координаты в Phaser 3.90

Оптимальный и рекомендуемый способ - использовать getBounds для вычисления реальных видимых размеров и координат.

1. Это позволяет работать с контейнерами, у которых нет width/displayWidth и прочих свойств
2. Это позволяет корректно вычислять координаты top, left, centerX, centerY независимо от origin

```typescript
const container = new Phaser.GameObjects.Container(scene, 0, 0, []);
// разумеется мы используем только те поля, которые нужны в логике
const { width, height, top, left, centerX, centerY } = container.getBounds();
```

Если мы собираем файлы в папку, создавай index.ts в ней, который экспортирует модули из файлов через \*

Это позволит компактно писать импорты таких файлов.

```typescript
export * from "./grid";
export * from "./mines";
```

## Типизация payload в switch
- Если в switch обрабатываются события с разными payload (включая void), внутри кейса можно явно привести: `const { durationMs } = data as OutGameUserLowLevelInput["onHintClick"];`.
- Перегрузки методов допустимы, но выбираем их только когда без приведения не обойтись и нужно строгая типизация без union void.
