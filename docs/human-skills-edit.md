# Как улучшить Skills

Внимание! Это в первую очередь инструкция для человека.

Ниже — мануал именно с состояния: **“кажется, мне что-то не нравится в skill, но я пока не понимаю что”**.

Skills в Codex устроены просто: skill — это папка с обязательным `SKILL.md` и, опционально, подпапками `scripts/`, `references/`, `assets/`. В `SKILL.md` обязательно есть метаданные `name` и `description`, а ниже — инструкции для агента. Codex сначала видит только метаданные, а полный `SKILL.md` читает, когда skill выбран явно или подошел по описанию. Поэтому при редактировании skill особенно важны две зоны: **description**, который отвечает за срабатывание, и **тело инструкции**, которое отвечает за поведение. ([OpenAI Developers][1])

## Фреймворк мышления: “что именно мне не нравится?”

Не начинай с правки текста. Начни с диагностики. Почти любая проблема со skill попадает в одну из пяти категорий.

Первая категория: **skill срабатывает не тогда**. Например, ты просишь “проверить сцену”, а Codex почему-то включает skill для создания новой мини-игры. Это проблема `description`. Codex использует описание skill для выбора, поэтому мутное описание приводит к неправильному запуску. ([OpenAI Developers][1])

Вторая категория: **skill дает слишком общий результат**. Например, вместо точных правок по файлам он пишет “улучшить архитектуру”, “разделить ответственность”, “подумать о тестах”. Это проблема тела инструкции: в skill недостаточно жестко задан формат результата, критерии готовности и запрет на абстрактные советы.

Третья категория: **skill делает лишнее**. Например, ты хотел только ревью, а агент начинает массово переписывать код. Это проблема границ: в инструкции не написано, какой режим работы нужен — “только анализ”, “предложить патч”, “сразу править”, “править только после подтверждения”.

Четвертая категория: **skill не учитывает структуру твоего проекта**. Например, он не понимает разницу между `auto_generated/` и `tuned/`, забывает про asset summary, игнорирует `common/`. Это проблема контекста: часть правил надо перенести в `AGENTS.md`, а часть — конкретизировать в skill.

Пятая категория: **skill нормальный, но устарел**. Например, ты поменял архитектуру Phaser-проекта, добавил новые папки, новые команды сборки, новый pipeline ассетов. Тогда надо обновлять не только текст skill, но и связанные справочники, шаблоны и, возможно, `AGENTS.md`.

Главное правило: **не редактируй skill по ощущению “он тупит”**. Сначала сформулируй дефект как наблюдаемое поведение:

```txt
Когда я прошу: ...
Skill делает: ...
Я ожидал: ...
Значит, надо изменить: trigger / порядок действий / формат ответа / границы правок / знание файлов.
```

## Где искать skill

В проекте skill обычно лежит здесь:

```txt
.agents/
  skills/
    phaser-scene-review/
      SKILL.md
```

Также skills могут лежать в пользовательской директории:

```txt
~/.agents/
  skills/
    some-skill/
      SKILL.md
```

Для репозитория Codex сканирует `.agents/skills` от текущей директории вверх к корню проекта. Глобальные и репозиторные настройки работают слоями: `AGENTS.md` задает постоянные инструкции проекта, а skills — специализированные workflow. ([OpenAI Developers][2])

## Какие файлы править

Минимальный skill:

```txt
.agents/skills/phaser-scene-review/
  SKILL.md
```

Расширенный skill:

```txt
.agents/skills/phaser-scene-review/
  SKILL.md
  references/
    project-structure.md
    review-checklist.md
  scripts/
    check-unused-assets.ts
    scan-scene-imports.ts
  assets/
    scene-template.ts
```

Правь `SKILL.md`, если проблема в поведении агента.

Правь `references/`, если skill ссылается на длинные правила, справочники, чеклисты, архитектурные соглашения.

Правь `scripts/`, если skill использует вспомогательные проверки и они дают неправильный результат.

Правь `assets/`, если skill берет оттуда шаблоны, заготовки, примеры файлов.

Правь `AGENTS.md`, если правило должно действовать **всегда**, а не только внутри одного skill. OpenAI рекомендует использовать `AGENTS.md` как постоянный источник инструкций и контекста проекта, который Codex читает перед работой. ([OpenAI Developers][2])

## Как понять, что именно править

### Случай 1. Skill не включается, когда нужен

Правь верхний блок `description`.

Плохо:

```md
---
name: phaser-scene-review
description: Helps with Phaser scenes.
---
```

Слишком широко. Codex может применить skill почти к чему угодно.

Лучше:

```md
---
name: phaser-scene-review
description: Use when reviewing existing Phaser 3 TypeScript scene files for dead code, duplicated logic, broken asset keys, oversized Scene classes, or unsafe refactoring. Do not use when creating a new mini-game from scratch.
---
```

Хорошее описание отвечает на два вопроса: **когда использовать** и **когда не использовать**.

### Случай 2. Skill включается слишком часто

Тоже правь `description`.

Добавь отрицательную границу:

```md
description: Use only when reviewing existing Phaser 3 scene code. Do not use for asset generation, game design brainstorming, writing new gameplay from scratch, or general TypeScript questions.
```

Здесь важно не превращать весь skill в список запретов. Но в `description` короткое “do not use when…” полезно, потому что это влияет на выбор skill.

### Случай 3. Skill дает слишком общий ответ

Правь нижнюю часть `SKILL.md`, особенно формат результата.

Плохо:

```md
Review the scene and suggest improvements.
```

Лучше:

```md
Финальный ответ должен быть только в таком формате:

1. Файл
2. Точная правка
3. Причина
4. Минимальный пример кода, если без него правка непонятна

Не давай общие рекомендации без привязки к файлу.
Не предлагай новые архитектурные идеи, если они не нужны для исправления найденной проблемы.
```

Для твоего стиля работы особенно важно явно писать: **“давать только действия”**.

### Случай 4. Skill слишком много переписывает

Добавь режимы правки.

```md
Режимы работы:

- Если пользователь просит "разбор", "ревью", "план" — только анализировать и выдавать список правок.
- Если пользователь просит "исправь", "внеси изменения", "пропатчи" — можно редактировать файлы.
- Если изменение затрагивает больше 5 файлов, сначала выдать план правок по файлам.
```

Это снижает риск, что агент начнет переписывать полпроекта, когда нужен только аудит.

### Случай 5. Skill путает автогенерированный и tuned-код

Правь тело skill и, возможно, `AGENTS.md`.

В `AGENTS.md` стоит держать постоянное правило:

```md
## Generated and tuned files

- scenes/auto_generated/ contains machine-generated files.
- scenes/tuned/ contains manually adjusted files.
- Do not edit auto_generated files unless the task explicitly asks for generator output changes.
- Prefer creating or updating tuned files when adapting generated views.
```

А в skill добавь конкретный workflow:

```md
Перед правкой:
1. Найди исходный файл в scenes/auto_generated/.
2. Найди tuned-версию в scenes/tuned/.
3. Если tuned-версии нет, создай ее.
4. Не изменяй auto_generated файл без явной команды пользователя.
```

Это пример разделения ответственности: `AGENTS.md` хранит общее правило проекта, skill хранит конкретный алгоритм.

## Практический алгоритм редактирования skill

### Шаг 1. Зафиксируй плохой пример

Создай маленький файл заметки, например:

```txt
.agents/skills/phaser-scene-review/debug-notes.md
```

И запиши:

```md
## Проблема

Запрос:
"Проверь ExampleScene.ts после рефакторинга"

Фактическое поведение:
Агент предложил общий план архитектуры и не указал точные файлы.

Ожидаемое поведение:
Агент должен выдать список точных правок по файлам.

Вывод:
Надо ужесточить формат ответа и добавить запрет на абстрактные рекомендации.
```

Этот файл не обязателен для Codex, но полезен тебе как журнал качества.

### Шаг 2. Открой `SKILL.md`

Пример:

```txt
.agents/skills/phaser-scene-review/SKILL.md
```

Проверь три зоны:

```md
---
name: ...
description: ...
---

Инструкции поведения...
```

Сначала смотри `description`. Потом — порядок действий. Потом — формат ответа.

### Шаг 3. Исправь `description`, если проблема в срабатывании

До:

```md
description: Reviews Phaser code.
```

После:

```md
description: Use when reviewing existing Phaser 3 TypeScript scene files for dead code, duplicate logic, broken asset references, oversized classes, or failed refactoring. Do not use for creating new games or generating sprites.
```

### Шаг 4. Исправь порядок действий, если skill делает не то

До:

```md
Review the code and suggest improvements.
```

После:

```md
Порядок работы:

1. Найди основной Scene-файл.
2. Найди связанные config, view, state, systems и asset-файлы.
3. Проверь импорты, публичные методы, события, asset keys и дубли логики.
4. Составь список точных правок.
5. Не переписывай код, если пользователь попросил только ревью.
```

### Шаг 5. Исправь формат ответа, если результат неудобный

Добавь жесткий шаблон:

```md
Формат ответа:

## Итог
Одна фраза: состояние сцены.

## Правки
Для каждой правки:
- Файл:
- Действие:
- Причина:
- Минимальный пример кода:

## Проверки
- npm run typecheck
- npm run build
```

Если ты хочешь, чтобы агент не расползался, формат ответа должен быть очень жестким.

### Шаг 6. Удали неоднозначные формулировки

Плохо:

```md
Improve architecture where possible.
```

Лучше:

```md
Выноси код из Scene только если:
- метод не использует Phaser lifecycle напрямую;
- логика повторяется минимум в двух местах;
- после выноса Scene становится короче и понятнее.
```

Плохо:

```md
Make code cleaner.
```

Лучше:

```md
Убирай:
- неиспользуемые импорты;
- неиспользуемые приватные методы;
- дублирующиеся literal-конфиги;
- asset keys, которых нет в manifest.
```

### Шаг 7. Если skill стал большим — вынеси справочник

Если `SKILL.md` разросся до огромного файла, вынеси детали:

```txt
.agents/skills/phaser-scene-review/
  SKILL.md
  references/
    phaser-review-rules.md
    project-folders.md
```

В `SKILL.md` оставь:

```md
Дополнительные правила:
- references/phaser-review-rules.md
- references/project-folders.md

Открывай эти файлы только если задача требует детального ревью.
```

Это соответствует принципу progressive disclosure: агент сначала видит метаданные, потом основной skill, а дополнительные материалы использует только при необходимости. ([OpenAI Developers][3])

### Шаг 8. Протестируй skill на трех типовых запросах

После правки skill проверь его не одним, а тремя запросами.

```txt
$phaser-scene-review Проверь scenes/tuned/GameScene.ts. Только ревью, без правок.
```

```txt
$phaser-scene-review Проверь scenes/tuned/GameScene.ts и исправь найденные проблемы.
```

```txt
Проверь, почему после рефакторинга GameScene стала хуже. Дай список точных правок.
```

Первый тест проверяет режим “только анализ”.
Второй — режим “можно редактировать”.
Третий — неявное срабатывание по описанию.

Codex skills можно вызывать явно через `$` или `/skills`, а также они могут выбираться неявно, если задача совпала с `description`. ([OpenAI Developers][1])

## Чеклист хорошего skill

Хороший skill отвечает на эти вопросы:

```txt
1. Когда skill должен включаться?
2. Когда skill не должен включаться?
3. Какие файлы сначала открыть?
4. В каком порядке работать?
5. Что считать готовым результатом?
6. Можно ли редактировать файлы или только анализировать?
7. Какие команды проверки запускать?
8. В каком формате вернуть ответ?
```

Для твоих Phaser-задач я бы держал такой стандарт:

```md
---
name: phaser-skill-name
description: Use when ... Do not use when ...
---

## Цель
Одна конкретная цель skill.

## Входные файлы
Какие файлы искать первыми.

## Порядок работы
Нумерованный алгоритм.

## Правила правки
Что и как менять.

## Проверки
Команды typecheck/build/test.

## Формат ответа
Жесткий шаблон финального ответа.
```

## Пример: было плохо, стало нормально

Было:

```md
---
name: phaser-autogen-to-tuned
description: Helps convert generated Phaser files.
---

Convert generated files to better code.
Clean up duplicates.
Improve structure.
```

Стало:

```md
---
name: phaser-autogen-to-tuned
description: Use when converting Phaser 3 TypeScript files from scenes/auto_generated/ into compact manually maintained files in scenes/tuned/. Do not use for creating new gameplay mechanics from scratch.
---

## Цель

Превратить автогенерированный Phaser view-файл в компактный tuned-файл без изменения визуального результата.

## Входные файлы

1. Исходный файл из scenes/auto_generated/.
2. Соответствующий файл из scenes/tuned/.
3. Config-файлы сцены.
4. Asset summary / manifest.
5. Общие helpers из common/, если они уже используются сценой.

## Порядок работы

1. Сравни auto_generated и tuned версии.
2. Сохрани визуальную структуру.
3. Перенеси ручные изменения только в tuned-файл.
4. Убери дубли создания объектов.
5. Вынеси размеры, позиции, asset keys и параметры анимаций в config.
6. Раздели создание UI на createBackground(), createHud(), createBoard(), bindEvents().
7. Запусти npm run typecheck.
8. Запусти npm run build.

## Формат ответа

- Измененные файлы
- Что упрощено
- Что вынесено в config
- Какие проверки прошли
- Что требует ручной проверки
```

## Когда править `AGENTS.md`, а не skill

Правь `AGENTS.md`, если правило касается всего проекта:

```txt
- версия Phaser;
- версия TypeScript;
- команды сборки;
- структура папок;
- где лежат автогенерированные файлы;
- где лежат tuned-файлы;
- какие файлы нельзя трогать;
- общий стиль кода;
- обязательные проверки.
```

Правь skill, если правило касается конкретного процесса:

```txt
- ревью сцены;
- создание новой мини-игры;
- аудит ассетов;
- перенос auto_generated в tuned;
- финализация билда;
- генерация конфигов.
```

Короткая формула:

```txt
AGENTS.md = постоянные законы проекта.
SKILL.md = сценарий выполнения конкретной задачи.
references/ = длинные справочники.
scripts/ = автоматические проверки.
assets/ = шаблоны и заготовки.
```

## Готовый мини-процесс “мне что-то не нравится”

Когда возникает ощущение “skill работает не так”, делай так:

```txt
1. Описать плохое поведение одним примером.
2. Определить тип проблемы:
   - не тот trigger;
   - слишком общий ответ;
   - делает лишнее;
   - не знает структуру проекта;
   - устарел.
3. Открыть .agents/skills/<skill-name>/SKILL.md.
4. Если проблема в запуске — править description.
5. Если проблема в поведении — править порядок работы.
6. Если проблема в результате — править формат ответа.
7. Если проблема в проектных правилах — править AGENTS.md.
8. Если текста стало много — вынести детали в references/.
9. Протестировать skill на 2–3 реальных запросах.
10. Закоммитить правку skill вместе с примером, какую проблему она исправляет.
```

Самая полезная привычка: каждый skill должен иметь не только инструкцию, но и **критерий хорошего результата**. Для Phaser это может быть так:

```md
Результат считается хорошим, если:
- сцена собирается;
- typecheck проходит;
- нет новых дублей;
- auto_generated файлы не изменены без явной команды;
- все правки привязаны к конкретным файлам;
- финальный ответ содержит только применимые действия.
```

Так skill перестает быть “советом для агента” и становится нормальным рабочим регламентом.
