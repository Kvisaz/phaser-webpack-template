Работай в режиме code review.

Учитывай `docs/ai/code_review.md`, `docs/ai/code_rules.md` и `docs/ai/layered-features.md`. Если документ противоречит реальному коду, явно отметь противоречие.

## Workflow

1. Запусти `git status --short` и определи все измененные, добавленные, удаленные, переименованные и неотслеживаемые файлы.
2. Изучи staged и unstaged изменения: `git diff --cached` и `git diff`. Для неотслеживаемых файлов прочитай содержимое напрямую.
3. Проверь только файлы из `git status`, но при необходимости открывай соседние файлы, публичные API, типы и места вызова, чтобы понять последствия изменения.
4. Не исправляй код во время ревью, если пользователь прямо не попросил это сделать.
5. Не запускай typecheck, lint, браузер или dev server без прямой просьбы пользователя. Можно рекомендовать `npm run typecheck`, если риск связан с типами.
6. Сфокусируйся на конкретных проблемах, которые могут привести к багу, регрессии, усложнению поддержки или нарушению архитектуры. Не превращай вкусовые предпочтения в findings.

## Checklist

Проверяй каждый измененный файл по этому списку:

1. Архитектурные слои:
   - импорт идет только из более конкретного слоя в более абстрактный;
   - код внутри слоя не тянет чужую фичу напрямую;
   - `shared` используется только для кода, который реально нужен нескольким фичам;
   - сцены собирают поведение, но не становятся складом бизнес-логики.
2. Границы абстракций:
   - новая абстракция решает повторяющуюся задачу, а не создана ради одного случая;
   - наследование, базовые классы, универсальные конфиги и дженерики не расширены без текущей необходимости;
   - публичный API не стал шире без реального потребителя.
3. Простота и объем кода:
   - изменение не добавляет многословные обходные пути для простой задачи;
   - нет дублирования, мертвого кода, лишних типов, лишних props, лишних констант и файлов;
   - код можно понять локально без длинной цепочки косвенных вызовов.
4. Игровая логика:
   - правила игры, тайминги, начисления, победа/поражение, блокировки ввода и переходы состояний не ломаются в крайних случаях;
   - изменение не создает гонки между анимациями, событиями, уничтожением объектов и пользовательским вводом;
   - Phaser-объекты корректно создаются, переиспользуются и уничтожаются.
5. Events и подписки:
   - для событий используется `SceneEvents<...>`;
   - `autoUnSub` передан, если подписчик умеет `destroy`;
   - локальные `events.ts` не экспортируются через `index.ts` и не импортируются между независимыми модулями;
   - request/response события подписываются на response до emit request.
6. Типизация:
   - нет `any`, неявных `any`, опасных кастов и ссылочной типизации вида `SomeType["field"]`;
   - props-объекты используются там, где аргументов больше двух;
   - типы и интерфейсы лежат в ожидаемых местах проекта.
7. Phaser 3.90:
   - Phaser не импортируется как модуль;
   - координаты и размеры не завязаны на некорректные `width/displayWidth`, когда нужен реальный bounds;
   - input events типизированы через `Phaser.Input.Events.*`, если это применимо.
8. Надежность:
   - нет утечек таймеров, tweens, listeners, ссылок на destroyed объекты;
   - асинхронные операции и callbacks не пишут в уничтоженные объекты;
   - ошибки и пустые состояния не приводят к падению сцены.
9. Тестовые и проверочные пробелы:
   - отметь, какие ручные или автоматические проверки нужны, если риск высокий;
   - не требуй тесты формально, если изменение маленькое и риск низкий.

## Findings

Выводи только реальные проблемы. У каждой проблемы должны быть:

- severity: `critical`, `high`, `medium`, `low`;
- точная ссылка `path:line`, если строка доступна;
- краткое описание;
- почему это важно для игры или архитектуры;
- два варианта эскиза решения.

Формат проблемы:

```md
- [severity] `path:line` - Короткое название проблемы.
  Почему важно: ...
  Вариант A: ...
  Вариант B: ...
```

Эскизы решения держи короткими. Если нужен код, добавь минимальный пример, а не полную реализацию.

Формат ответа:

```md
## Findings

- [severity] `path:line` - проблема.
  Почему важно: ...
  Вариант A: ...
  Вариант B: ...

## Questions

- ...

## Checks

- `git status --short`: checked
- `git diff --cached`: checked
- `git diff`: checked
- `npm run typecheck`: not run (not requested)

## Summary

Кратко, только если нужно.
```

Если проблем не найдено, скажи это явно и укажи остаточный риск.

Если пользователь просит записать ревью в файл, используй путь из запроса или `reviews/current-changes-code-review.md` из `docs/ai/code_review.md`. В файл также включай итоговый список проблем с двумя вариантами решения для каждой найденной проблемы.
