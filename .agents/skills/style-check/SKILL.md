Проверяй только текущие изменения из `git status`.

## Порядок работы

1. Выполни `git status --short`.
2. Прочитай список измененных файлов.
3. Для измененных TypeScript-файлов прочитай diff через `git diff -- <path>` и, если нужно, сам файл.
4. Прочитай `docs/ai/code_rules.md`; если вопрос касается слоев, также прочитай `docs/ai/layered-features.md`.
5. Оцени изменения по чек-листу ниже.
6. Запусти `npm run typecheck`.
7. Если typecheck падает, исправь ошибки наиболее разумным способом, не расширяя scope.
8. После исправлений повтори `npm run typecheck`.

## Чек-лист автоматических исправлений

Проверь:

- не нарушены правила из `docs/ai/code_rules.md`
- добавление в существующий код сделано либо парой строк, либо через новую функцию/метод, который точечно вызывается в старом коде
- допускается точечный вызов нескольких новых функций/методов
- большие блоки логики не добавлены внутрь существующих функций и методов
- новый код не создает ненужные функции-обертки; признаки нарушения: функция слишком тонкая, одноразовая, а при ее устранении количество кода падает
- дополнительные функции идут после основной функции/класса в теле файла
- дополнительные функции объявлены через `function`, а не через `const fn = ...`, если нет сильной локальной причины
- все типы и интерфейсы, кроме props и args, лежат в `types.ts`
- props для класса лежит рядом с классом
- args, то есть объект-аргумент функции, типизируется перед самой функцией
- args-тип не выносится в общий `types.ts`, если он нужен только одной функции
- не добавлены лишние абстракции, конфиги и универсальные helpers без реальной необходимости
- связанные константы не размазаны набором `SOME_CONST`; если их больше одной, они собраны в `someNameConfig = { ... }`
- новые ручные компоненты в `src/scenes/auto_tuned/` не зависят от construction-утилит из `auto_generated/utils/utils`; допустимы generated data/types/configs
- интерактивность `Phaser.GameObjects.Container` сделана через `makeContainerInteractive` из `common`
- новые функции, методы и классы прокомментированы `/** ... */` на русском перед названием
- ключевые моменты кода, отвечающего за сложную верстку нескольких объектов, математические вычисления и сложные логические комбинации, прокомментированы `/** ... */` на русском
- используется `makeAlign` вместо создания нового инстанса `Align`

## Нарушения архитектуры
Случаи ниже следует отметить в анализе и предложить варианты исправлений, но самому не править.

- Общий код патчится ради частного случая
- Абстрактный класс или интерфейс становится менее абстрактным
- Код становится хрупким и может сломаться от другой комбинации факторов в этой же игре

## Исправления

Если найдено нарушение, исправь его.

Правь минимально:

- не переписывай соседний код без необходимости
- не меняй публичный API, если можно сохранить
- не трогай unrelated files из `git status`
- не откатывай чужие изменения
- при перемещении файлов используй `git mv`

Если typecheck выявил ошибку, исправь ее по смыслу, а не через подавление типов.

## Формат ответа

Выведи список правок и объяснение причины строго в формате:

```md
1. `path/to/file.ts` -> `FunctionOrClassName` -> нарушение
   Что исправлено:
   Обоснование:

2. `path/to/other-file.ts` -> `FunctionOrClassName` -> нарушение
   Что исправлено:
   Обоснование:
```

Пункты списка разделяй пустой строкой.

Затем выведи список критических нарушений архитектуры и предложени по их правке,
отделяя их большой линией =======
```md
1. `path/to/file.ts` -> `FunctionOrClassName` -> проблема
   Обоснование:
   Вариант правки 1:
   Вариант правки 2:

2. `path/to/other-file.ts` -> `FunctionOrClassName` -> проблема
   Обоснование:
   Вариант правки 1:
   Вариант правки 2:
```

Если нарушений не найдено, напиши:

```md
Нарушений style-check не найдено.

Typecheck: прошел.
```

Если typecheck не удалось запустить, явно укажи команду, ошибку запуска и что осталось непроверенным.
